# keikaku — the stages, in order

**This is the pipeline the orchestrator runs** (`house/orchestrator.py`, `STAGES`): what runs, in what order, on which model, and what code enforces. `ARCHITECTURE.md` and `STORY-STATE.md` explain why. When another doc disagrees with this one about the order of work, this one is right, and a change goes here first.

## Units

- **Work:** one text. **Run:** one pass of a work through the house. **Segment:** a paragraph of the source, `p12`. Sentences inside it, `p12-s3`, exist only as anchors for notes.
- **The paragraph is the unit of English.** Translation returns one English string per paragraph (or per group, below). Nothing forces one English sentence per Japanese one; a literary translator restructures, and a sentence-locked schema would push the model back towards literalism. The parallel layout aligns paragraph to paragraph, always.
- **Page:** the unit of *translation*. A drafting chunk of about 650 characters (~1k source tokens) of whole paragraphs, breaking at scene breaks where possible. The paragraph is only where the English is *stored* and *aligned*; nothing is translated a paragraph at a time, except paragraphs a draft left out (below). Revisions, readers' notes and labels are recorded per paragraph.
- **Part:** the unit of *reading*. The readers, the desk, the final read (on a long text) and the notes work a part at a time: what one careful reader can judge whole, at most 25,000 characters (`context.MAX_PART_CHARS`). The planner proposes the parts; a short story is usually one part.
- **IDs are in the prompt.** Paragraph IDs (`p47`) come from the parser, in source order, and never change. The drafting call receives its paragraphs with their IDs printed and answers keyed by the same IDs; the readers' notes, the desk and the edit tool use them too. Pages are an internal unit for calls and budgeting only: no reader sees a page number.
- **Groups.** When the English wants two short source paragraphs as one, the drafter returns the English against a group of paragraphs (`p21–p23`); alignment is group to group for that stretch. The release puts the group's English on its first paragraph and marks the others as carried by it.
- **What a paragraph is** is decided by the parser from the source (line breaks, the indent mark, dialogue lines on their own line), deterministically, before any model sees the text. A dialogue line is a paragraph.
- **One path.** Every paragraph goes through the same stages.

## The stages

Each stage is a module `house/stages/<name>.py` with `run(ctx)`, which records what it does as events and returns a summary for the `stage.done` event. The orchestrator can stop and resume between any two stages.

Spark is `muse-spark-1.3`, Wonder is `muse-wonder-1.0`. Every call sends the house brief (`prompts/house-brief.md`) and then its department's prompt. The run options and their defaults are `DEFAULTS` in `house/stages/common.py`; the command line sets them with `--draft-model`, `--reader-model`, `--desk-model`, `--final-model` (`spark` or `wonder`), `--draft-prompt`, `--voice N` and `--checkpoint`.

Code checks the answer starts at the first paragraph, runs in order, names only real paragraphs and has no part over 25,000 characters. Two things were tried and dropped in experiment 3 (`experiments/03-stiffness.md`): a model picking among page-1 drafts in each voice, and a translator re-reading its own part before the readers. Neither helped. The checkpoint brings the voice choice back for a person to make.

## The checkpoint

With the run's `checkpoint` option on (`keikaku run <work> --checkpoint`; runs started on the editors' desk have it on unless the start request turns it off), the checkpoint drafts page 1 once in each voice take, side by side, with the run's own drafting prompt and model. The drafts go in the run's `checkpoint` document: none of them is the run's English yet. The run is set `waiting` (`checkpoint.waiting`, `run.paused`) and the orchestrator stops. While it waits, the editor can:

- **Send a note** (`keikaku steer <work> "note"`, `house/steer.py`). One `steer` call reads the reading and the bible as stored and as the editor rewrote them, page 1 as it stands, the notes so far and the house's replies, and the new note, quoted as the person's own words to interpret. It carries the note into the reading and the bible as house style, never as a request, and replies: what it changed, what it didn't and why, and a question if it has one. New versions of the reading and the bible are saved only where they differ, and page 1 is drafted again in the current voice under them.
- **Rewrite the reading, the voices or the bible by hand.** `keikaku checkpoint <work>` writes `reading.md`, `voices.md` (each voice's name and line, then page 1 in it) and `bible.md` to `checkpoints/<work>/` in the data folder, exactly as every later call reads them; a hand edit is taken by the next `checkpoint`, `steer` or `approve`. The editors' desk has a box for each. Every later call reads the editor's version. A file can't grow past three times what the house wrote, or 6,000 characters if that's more.
- **Rewrite page 1 in a voice** (on the desk). If the run is approved in that voice, the draft takes the page as it is, and every later page matches it as the voice reference. A later note that redrafts that voice's page replaces it, and the log says so.

Every hand edit, and every note's change to a hand-edited file, is a new version of the document with a `document.edited` event holding before and after. The loop ends only when the editor approves: `keikaku approve <work> --voice N` records the voice in the run's options and sets the run `queued`; `keikaku run <work> --from draft` carries it on. A run resumed from an earlier stage after approval doesn't wait again. When nothing has changed since page 1 was last drafted in the approved voice, the draft's first call is the same call and comes from the cache. What the editor sees of all this is `EDITORS-DESK.md`.

## How pages are cut and handed over

Code, before any model is involved.

1. **The parser** turns the source file into an ordered list of paragraphs with IDs, marking scene breaks (blank lines, section numbers, Aozora's ※ and ◇ markers) and dialogue lines.
2. **The pager** (`house/pager.py`, deterministic) walks the list and builds pages: it adds whole paragraphs until the next would take the page past the target (650 characters), closing early at a scene break once the page is past 60% of the target. It never splits a paragraph; a paragraph longer than the target is a page on its own.
3. **The draft stage** goes page by page in order, assembles the context (`STORY-STATE.md` §3) and makes one drafting call per page.
4. **The answer** is a list of items, each naming the paragraph IDs it covers (one, or a group), with the English and translator's notes. Code keeps what the answer got right: a paragraph not on the page is dropped (the drafter sometimes translates the next paragraph it was shown), and a paragraph drafted twice keeps its first draft. Paragraphs left out are flagged and drafted again in one more call, as a page of their own; left out twice, the stage fails. Then it stores a revision per paragraph or group, emits events, and moves on.

The model never decides where a page starts or ends and never sees half a paragraph. The only division a model makes is the planner's parts, which decide what the readers, the desk, the final read and the notes judge at once, never what a drafting call drafts; and code checks those.

## How the readers and the desk work

No agent talks to another agent. There's no shared chat, no transcript passed around, and no agent chooses who to address. Think of a publishing house where two readers mark up a part in the margin, separately, and one desk editor goes through both sets of notes and decides. Three findings shaped it: a model revising its own draft favours it (Xu et al. 2024), rounds of debate talk agents out of right answers (Wynn et al. 2025), and readers of the English alone reward a fluent translation that has drifted from the source (Wu et al. 2025; Ferstler et al. 2026). Full references are in `REFERENCES.md`.

| Step | What happens | Who | Call |
|---|---|---|---|
| 1 | The translator drafts every page of the text, in order | translator | `translate-draft-plain` per page |
| 2 | The faithful reader and the readable reader each read the part, independently, and leave notes or none | readers | `reader-faithful`, `reader-readable` per part |
| 3 | Code stores each note as a query owned by the desk; a note anchored outside the part is flagged and dropped. The desk sees them numbered per part (F1… and R1…) | code | none |
| 4 | If there are notes, the desk weighs them against the reading and the translator's notes. It makes its changes with the edit tool, each naming the notes it answers, then answers with the notes it declined and why, every place the readers pulled opposite ways, and anything it learned that changes an earlier part. An answer that decides none of the notes is asked for once more, saying so | desk | `desk` per part |
| 5 | Code stores a revision for each changed paragraph and checks it (no stray script, not shrunk below 70%), flagging what fails. It marks each note *taken*, *declined* or *forked*, and *unaddressed*, with a flag, if the desk didn't decide it. Disagreements are recorded beside the line; the ones the desk sends up become forks for the editor | code | none |

That's all: no answer from the translator, no re-check, no rounds. The margin for a paragraph is the readers' notes and the desk's reasons, with the revision they caused. The final read is the whole-text check on what the desk changed.

**The edit tool** is the one tool the desk, the final read and the copy editor share (`house/stages/common.py`, `Editor`): `edit(old, new, reason, replace_all)`, with the notes it answers for the desk. It works on the paragraphs the call was given. The words must appear exactly once, or `replace_all` changes every place they appear; an edit stays inside one paragraph. A refused edit changes nothing and goes back to the model with why and, for words found more than once, where they are, so it can try again. The copy editor also has `find`, which shows where words appear and changes nothing.

**When a later part changes an earlier one: the emergency lever.** The desk may say that something it learned in this part changes how an earlier one should read: who a character is, what a word means here. Later parts' desks are told. Once every part has been through the desk, each earlier part goes back to it once, with the findings from the parts after it as its notes (S1, S2…), to act on or decline. No human is needed, and nothing loops: at most five findings a run, one pass back; a finding made on the way back is recorded, not taken back again.

**Why it can't explode.** The graph is a straight line per part: draft, two readers, desk. Schemas cap each reader at twenty notes a part; a reader may always answer "none"; a part with no notes skips the desk. A tool loop is told to answer after 12 turns (30 for the copy editor) and fails if it goes on. On top sit the up-front estimate and the spend caps. Nothing in this section is asked of the prompts; it's all code.

## Stop and resume

Every stage writes its outputs to the database before the next starts, so a run can stop after any stage and resume from the record (`keikaku run <work> --to <stage>`, then `--from <stage>`; `--only <stage>` runs one). The draft, readers, desk, final read, copy desk and notes also skip what's already done, so a stage cut off half-way resumes where it stopped. The response cache (model, effort, prompt, input, schema, tools, earlier tool turns) makes a resumed or repeated call free. A resumed run keeps its own options and parts, and its cap unless a new `--cap` is given.

- **A stage that fails** records `stage.failed` with the error, and the run stops there with status `failed`; the message says how to resume.
- **A run the budget stops mid-way** records `run.stopped`, releases nothing, and says which cap to raise and how to resume.
- **A run with a checkpoint** stops after the bible with status `waiting` and goes on only once it's approved (above). Without the option a run goes straight through unless it's told where to stop.
